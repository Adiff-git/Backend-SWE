## D01 — Lifecycle and variant persistence (FR-003/005/013/016/032/033/036; BR-01/06/10–12/14/17/20)

**Decision**: Add UNPUBLISHED to existing ProductStatus and CHECK; keep existing values unchanged. Add non-null enabled boolean default true to variants. No separate lifecycle table/flags or destructive replacement. Variantless Drafts and logically Archived variantless Drafts are valid; preparation Unpublished may be incomplete under basic rules. Published requires at least one Enabled valid variant and every Enabled sale-valid variant. Existing mandatory SKU/price and all-variant option integrity remain.

**Rationale**: E01–03 show the exact unconditional child-count constraint; nullable price or fake child would solve the wrong problem. One extra enum value is the smallest explicit representation of BR-20. A nullable last_restored_at timestamp exposes initial versus restored Draft provenance required by FR-002, without inventing a full lifecycle ledger. Enabled is orthogonal to status and stock. **Alternatives**: DRAFT plus everPublished flag adds historical inference and ambiguity; separate catalog/variant copies duplicate persistence; soft-deleting variants would wrongly free identity or lose attribution.

## D02 — One publication validator and final integrity (FR-005/008/014/015/020/022/024)

**Decision**: ProductPublicationValidator accepts a prepared proposed Product+category context+all variants+active gallery. It delegates basic rules to CatalogDataValidator/TechnicalSpecificationValidator and aggregates safe path violations. It requires ≥1 Enabled, all Enabled strictly positive exact finite whole-VND prices, valid global identities, valid metadata gallery with exactly one primary, required name/category and applicable supported facts. Disabled remain basic-valid; no inventory lookup. Call on Publish and every mutation whose resulting Product is Published, including association edits and affected category changes. Database adds structural final-commit cross-row guards; application gives richer feedback.

**Rationale/alternatives**: E02–06 do not implement complete readiness. Reusing the all-status minimum validator unchanged breaks Drafts. Controller copies, availability-as-readiness and global positive-price CHECK would contradict BR-14/17. No mandatory nonempty facts, positive stock or new model registry.

Technical facts: accept the exact version1 envelope and generic typed canonical facts. When a registered fact is supplied in an applicable family, enforce the registry type/unit using the same existing applicability resolution; nonapplicable generic facts remain stored, not falsely searchable. Unknown but structurally valid canonical keys remain generic facts. Do not silently activate unsupported keys. Existing read-time quality exclusions are not a mandate to invent/repair values. A category change is rejected if a real applicable validation rule would invalidate Published data; the current code has no universal category-required facts. AC-43 tests can use a known registered value that becomes applicable with the wrong type/unit, not invented mandatory fields.

## D03 — Preserve dynamic category applicability (FR-009/012/023/034)

**Decision**: Keep the current approved named Laptop/Tablet-family resolver, ancestry boundary and missing/ambiguous disable behavior; make its resolution reusable by admin validation without duplicating a divergent Java tree algorithm. Extend the catalog repository query fragment with a bounded applicability projection driven by the same SQL fragment/constants. Test rename/reparent/duplicate names and affected Published proposals using current and proposed topology. Category operations inspect all potentially affected Published products; because name uniqueness is global in the family resolver, rename/create/delete can affect products outside the moved subtree.

**Rationale**: E06–07 expressly approve disable-on-ambiguity, while BR-19 permits repeated names under different parents. Both can hold: duplicate allowed, affected filter binding disabled as today. Report this observable consequence in admin category change results (`affectedBindings`), with no fabricated repair or generic rejection solely for duplicate names outside siblings. **Rejected**: global category-name uniqueness violates BR-19; a stable family-root binding table would change approved registry semantics and needs separately scoped policy. This is a technical compatibility risk with defined behavior, not an unanswered business question.

## D04 — Revision boundary and hierarchy gate (FR-029; BR-15/16)

**Decision**: Product has one BIGINT revision for fields/status/all owned variants/prices/facts/active gallery. Category and Brand have individual revisions. A single catalog_taxonomy_state row supplies taxonomyVersion and a transaction-scoped shared/exclusive gate. Conditional UPDATE WHERE version=expectedVersion claims each mutable aggregate and increments its revision in the same transaction. Product child-only writes must claim Product first. No entity @Version is required on children; do not mix unmanaged native increments with stale managed @Version state. Fetch after claim, flush deterministically, and read current revision for response. Every supported catalog writer uses this protocol; quiesced imports/bootstrap must adopt it before future concurrent use.

**Rationale**: E08/12 and existing V3 locks mean row-version-on-Product alone does not cover children, checkout or cycle phantoms. One gate row lets rare topology changes exclude product assignments and shared admin validation without distributed locking. Category updates use own expectedVersion plus expectedTaxonomyVersion; all product updates use both Product and taxonomy observed versions. Brand rename/delete uses only Brand revision; product brand assignment checks the referenced Brand under a share lock and supplied expectedBrandVersion when selecting a brand. Creation of a new Draft still requires only name+category; no pre-existing Product version is required.

**Alternatives**: automatic retry/merge violates BR-15; SERIALIZABLE changes default isolation and still needs retry policy; per-child versions alone permit conflicting last-variant/gallery decisions; global catalog version would serialize unrelated price edits unnecessarily. See exact lock and response rules in consistency.md.

## D05 — Names and race-safe integrity (FR-012/014/034/035)

**Decision**: Use one immutable PostgreSQL name-key function for case-folded comparison after outer-whitespace trim. Explicit shared trim character set covers U+0009–000D, U+0020, U+0085, U+00A0, U+1680, U+2000–200A, U+2028–2029, U+202F, U+205F, U+3000; no internal-space collapse, accent folding or alias merging. PostgreSQL LOWER under the target collation is authoritative; input uniqueness checks call the same repository normalization expression/function, not independent Java casing. Persist trimmed display case. Reject empty normalized names. Confirm database collation during preflight and keep it stable for the index lifecycle.

Create a global unique brand-name-key expression index and separate partial category sibling/root unique expression indexes, preserving brand code and all-row lower(sku) uniqueness. Input checks improve feedback; named DB violations settle races. Do not change SKU identity to name normalization or free disabled/archived identities. Existing product names remain nonunique.

**Alternatives**: ASCII-only btrim misses agreed whitespace classes; independent Java strip/lower and SQL btrim/lower can disagree; one nullable-parent UNIQUE allows duplicate roots; global category uniqueness rejects allowed data. No new dependency is needed.

## D06 — Gallery retention and ordering (FR-018–021/031)

**Decision**: Add active boolean default true to product_images. DELETE association sets active=false and primary=false, retaining the row, durable key, source identity and legacy upload FK. All public/admin-current gallery, count/primary, cart/order/recommendation image queries and deferred gallery checks filter active; internal reconciliation still sees all retained rows. Keep global object-key/source-image identity uniqueness. Reattachment of a detached same product/source reactivates the existing association after owner/content/version checks, not a conflicting duplicate insert. No object delete.

Keep active gallery positions as nonnegative integers; replace all-row order unique with active-only unique (product_id,display_order), and primary unique with active-only primary predicate. Reorder may temporarily use free nonnegative INTEGER positions, then final0..n-1; choose gaps safely by scanning ≤10 active occupied values, never max+offset arithmetic that can overflow. Clear old primary before setting designated replacement in the same transaction; deferred exactly-one checks final state. No automatic replacement on removal. Attachment preserves first-image-primary behavior.

**Rationale**: E04 legacy published upload cannot lose its nonnull FK. Physical row deletion or clearing legacy references would rewrite history and needs more schema/state surgery. Logical membership is the smallest data-preserving option. Countervailing cost: retained inactive rows/objects and every consumer predicate need explicit regression coverage; cleanup remains reference-safe, not a new retention job.

## D07 — Media workflow and legacy route (FR-018/021/029)

**Decision**: Reuse current upload/completion. Extend MediaService with prepared product-image ownership/completion/version metadata and command-time revalidation, analogous to its review-image pattern. Catalog owns product-content decode/copy/hash/checkpoint; network occurs before short catalog command transaction. The legacy POST /api/products/{id}/images delegates to the same command and now requires expectedVersion/expectedTaxonomyVersion. Check these before any replay succeeds; stale identical retry returns409 and reload is required. Current-version identical attachment returns200 with no new revision/write; new attachment/reactivation returns201.

**Rationale**: E08–09 show real reuse and the otherwise unprotected replay path. New attachments require original upload ownership; publishing/viewing another Admin's attached images does not. Failed DB commit may leave a private copied object; do not delete it on guessed absence or assume rollback. Retain existing safe reconciliation/checkpoint pattern.

## D08 — HTTP/security/error integration (FR-001/025/030)

**Decision**: Admin prefix /api/admin/catalog, typed direct DTOs and JSON/query revision preconditions; no ETag/CORS changes needed. Scoped admin controllers use a code-preserving advice backed by ApiErrorFactory. Restrict old bare catalog advice to assignableTypes ProductCatalogController only; admin advice uses assignableTypes for the five admin controllers plus legacy ProductImageController. Do not use basePackageClasses for this exclusion, because it still selects subpackages. Equal HIGHEST_PRECEDENCE ordering must never leave overlapping applicability. Preserve old public error shape. Exact ADMIN JWT matchers on the established chains, current authority checks and no caller identity field.

**Rationale**: E16–17 expose deny-all defaults and loss of exception properties. Merely adding exceptions or @PreAuthorize does not solve those transport issues. Shared Security ProblemDetail entry/denial handling remains unchanged. Contract defines400/401/403/404/409/415/422/503 and named errors; unknown SQL faults stay500.

## D09 — Cross-module behavior and rollout (FR-017/026–028)

**Decision**: Publication+enabled+strictly-positive current sale price forms catalog sale eligibility; stock remains owned Inventory availability. Internal CartVariantState/CheckoutVariantState gain enabled, not new customer fields. Reuse existing unavailable masks/reasons and partial checkout selection. Keep receipt replay before mutable checks, historical order data unchanged, zero balance trigger and order-owned allocation resolution. Extend search candidate/facts and recommendation snapshot/refresh; no AI HTTP changes. Public variants exclude Disabled; admin includes all.

**Rationale**: E10–15 establish actual integration. Parent row claim before children serializes with checkout share locks; user/cart/order/inventory locks are never acquired by admin changes. Coordinated deployment is mandatory, since old binaries ignore new fields/state. No automatic legacy-data normalization, publication withdrawal or stock fabrication.
