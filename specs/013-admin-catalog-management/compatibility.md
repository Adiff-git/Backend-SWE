## Administrative capability gaps

Current main catalog controllers expose public catalog reads and completed-image attachment; Category and Brand have entities/repositories but no separate administrative controllers. No main-source workflow was found for Draft create/edit, Publish/Unpublish/Archive, taxonomy maintenance/dependency-safe deletion, variant CRUD/disable, direct variant-specification administration or complete gallery edit operations. Controller/service presence is not treated as proof of complete administration. The audit independently records these gaps.

The existing ProductImageService attachment includes upload validation and primary selection on attachment. That concrete capability must be reused, not mislabeled wholly absent. Public-only product reads are insufficient for administrator inspection of Draft/Archived data. Current identities/source links, order snapshots and reservation history must remain preserved.

## Existing Data and Constraint Readiness

Source-level compatibility is confirmed; **current target database contents are unknown**. No target was connected, no data or schema was changed, and no historical pilot report establishes present data cleanliness.

- Categories currently have no sibling-name uniqueness constraint. Existing equal normalized names within one parent, including all root categories, may conflict with BR-19/CQ-12. A reparent can create a destination conflict even if the original tree is unique. Names repeated under different parents are explicitly allowed and must not be globally merged or prohibited.
- Brands currently constrain unique `code`, not normalized `name`. Different codes/IDs can therefore have equal case/outer-whitespace-normalized names. Products in any lifecycle, including Archived, may reference those identities; collision resolution cannot silently detach/merge them. Existing canonical brand alias documentation does not authorize new fuzzy/normalized identity merging.
- Product names have no existing uniqueness constraint and may remain duplicated. Existing case-insensitive SKU constraints should be retained across Enabled/Disabled and Archived ownership; do not filter uniqueness to visible/sellable rows. Include referenced retained rows when examining conflicts.
- Existing Published rows may have zero/negative preparation prices, no valid imagery or newly incompatible category facts while satisfying older constraints. Such cases are possible from the inspected schema, not confirmed live rows. Inventory zero is not a publication defect. Plan must identify actual violations and data-remediation needs before migration/rollout design without silently bulk-unpublishing, repricing, fabricating images/variants or erasing history.
- Existing referenced categories, brands, variants, media, source links, orders and reservations make collision handling data-preserving work. Record affected identities/dependencies and obtain any separately required data-remediation authorization; clarification does not authorize destructive cleanup.
- Required preflight outcomes before migration design are actual duplicate groups under the approved equality/scope, relevant references, Published-readiness incompatibilities and any hierarchy cycles. This is a dependency description, not a SQL script, migration design or execution claim.

Source references above remain at the recorded application baseline. In particular, `V1__create_catalog_core.sql` and `V11__catalog_data_enhancement.sql` show the name-constraint gaps, `ProductVariant.java` shows no disable/version field, and `Brand.java` retains stable code. Application data, migration history and external deployment configuration were not inferred from the audit's isolated tests.
