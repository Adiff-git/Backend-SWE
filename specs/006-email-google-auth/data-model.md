# Data model

All new persistence is auth-owned; users/password/official-email mutations remain user-owned. Preserve existing BIGINT user IDs and UUID application sessions. Durable auth rows use generated BIGINT IDs unless the public UUID is itself their primary key below. All absolute timestamps use Instant/TIMESTAMPTZ. New Flyway versions follow the actual current inventory, including existing V12; never edit applied migrations.

## User changes

users.password becomes nullable TEXT, retaining nonblank-if-present and existing BCrypt rows. Null means no local credential. email_verified_at is nullable TIMESTAMPTZ for the current official address only. Historical email remains unverified. Email may be null for legacy users only; enforce new-account email requirements through creation services without invalidating old rows. Existing case-insensitive username/email uniqueness remains authoritative. Derive username from normalized email local part, suffix _2/_3 on collision, truncate base to fit 50 Unicode code points; never rename on email change. Private response exposes emailVerified and hasLocalPassword; provider status is auth-owned separately.

## pending_registrations

id UUID PK; destination VARCHAR(254) normalized lowercase NOT NULL; credential_hash BYTEA nullable only after terminal secret erasure, 32 bytes when present; generation INTEGER NOT NULL >=1; state VARCHAR enum ACTIVE/CONFIRMED/CONFLICT/EXPIRED; created_at, expires_at NOT NULL; consumed_at, expired_at nullable. Current challenge is related by pending_registration_id plus generation, not a cyclic parent FK. No user FK, username, password hash or plaintext password. No unique destination constraint: unrelated attempts may coexist and neither reserves users.email/username. Index destination and expires_at. credential_hash UNIQUE when present, opaque credential generated from 32 random bytes; public id alone is not authority.

Initial creation atomically writes generation 1, challenge and encrypted outbox in one business transaction. Return the initiating credential only after commit. Rollback leaves none of these records. Confirmation validates credential/current challenge/code and newly supplied password, then atomically creates verified user, role, provider-independent application session/refresh and consumes proof. A winning official-email uniqueness conflict rolls back all creation; a fresh outcome transaction may mark the losing pending attempt CONFLICT but never authenticate an existing account. Successful concurrent confirmations of one attempt yield at most one token response; replay fails generically. Do not return a previous token result on replay.

Resend locks the same pending row and requires current credential/challenge. Rotate credential hash and generation, supersede old challenge/outbox, create a fresh ten-minute challenge, set expires_at to that challenge's deadline and commit both replacement secrets atomically. independent attempts for the destination are not superseded. Missing credential cannot recover by public ID/email alone: start an independent attempt. Delivery failure does not roll back pending creation; lost resend response likewise requires an independent attempt if the old credential is no longer valid. Terminal pending secrets are erased no later than 24 hours after expiry; FK-safe row cleanup follows challenge/outbox cleanup.

## email_verification_challenges

id UUID PK; user_id BIGINT nullable FK users; pending_registration_id UUID nullable FK pending_registrations; generation INTEGER >=1; destination VARCHAR(254) lowercase; purpose REGISTRATION/EMAIL_CHANGE; code_mac BYTEA (32 bytes while active); key_id; created_at/expires_at; active BOOLEAN; consumed_at/superseded_at nullable; delivery_status QUEUED/SENT/FAILED/EXPIRED.

CHECK exactly one of user_id/pending_registration_id is non-null. Pending owner permits REGISTRATION only; EMAIL_CHANGE requires user owner. Historical unverified users may own REGISTRATION challenges. Partial unique indexes permit at most one active challenge per (pending owner,purpose) or (user owner,purpose); unrelated pending owners can share destination. Current pending generation must match confirmation and resend; increment/replacement under parent lock. Six-character numeric code includes leading zeros, ten-minute expiry. HMAC binds challenge ID, owner kind/id, destination, purpose and code; keys outside DB, constant-time compare. Never store raw code in challenge. Wrong codes leave the challenge usable until expiry, supersession or consumption. At now >= expires_at the challenge is invalid independent of cleanup. Registration for existing user must still target its current official address. Replacement confirms with recent EMAIL_CHANGE proof, rechecks uniqueness and atomically replaces evidence/consumes related state.

## google_identities

id BIGINT PK; user_id BIGINT FK users NOT NULL; provider GOOGLE; issuer TEXT NOT NULL canonical validated https://accounts.google.com; subject nonblank opaque case-sensitive TEXT; provider_email nullable VARCHAR(254); linked_at NOT NULL immutable; last_successful_login_at nullable until a successful login. UNIQUE(provider,issuer,subject) and UNIQUE(user_id,provider). No provider tokens/picture URLs. New Google registration requires valid verified email, creates user+association at LOGIN exchange; pending local rows do not reserve email. Returning identity resolves by issuer/subject; metadata cannot overwrite official email/profile.

## recent_auth_proofs

id UUID PK; secret_hash BYTEA UNIQUE 32-byte digest; owner_user_id BIGINT FK; initiating_session_id UUID FK; method PASSWORD/GOOGLE; operation EMAIL_CHANGE/INITIAL_PASSWORD/CONNECT_GOOGLE; provider_identity_id nullable FK; authenticated_at/expires_at NOT NULL; consumed_at nullable. Expiry = actual authentication + five minutes, never exchange/refresh time. INITIAL_PASSWORD requires GOOGLE proof of already linked identity; EMAIL_CHANGE and CONNECT_GOOGLE use password when set or already linked Google when absent. All proofs bind owner, original active session and operation. A new identity being linked cannot issue CONNECT_GOOGLE proof for that owner. Successful sensitive mutation consumes proof; expired/replayed/misbound proof fails, with no partial association or credential mutation.

## oauth_login_attempts and oauth_handoffs

Attempt: id UUID PK; start_ticket_hash BYTEA UNIQUE; purpose LOGIN/LINK/REAUTH; operation nullable EMAIL_CHANGE/INITIAL_PASSWORD/CONNECT_GOOGLE; owner_user_id/initiating_session_id nullable only for LOGIN; recent_auth_proof_id nullable FK, required for LINK; destination_key from configured allowlist; pkce_challenge CHAR(43); browser_slot_id UUID FK; browser_generation INTEGER; browser_binding_hash BYTEA; oauth_state_hash BYTEA UNIQUE; encrypted_request BYTEA with key_id/nonce; status CREATED/STARTED/CALLBACK_VALIDATED/FAILED/EXPIRED; created_at/expires_at/consumed_at. Five-minute attempt. LINK requires operation CONNECT_GOOGLE; REAUTH requires an operation. Serialize only constrained framework request attributes, never arbitrary Java objects or provider tokens.

Handoff: id UUID PK; code_hash BYTEA UNIQUE; attempt_id UUID FK; purpose/operation; validated issuer/subject/email/verified claim/initial display name; owner_user_id/initiating_session_id and recent_auth_proof_id copied immutably; browser_slot_id/generation; pkce_challenge; authenticated_at; created_at/expires_at/consumed_at. 60-second expiry. LOGIN creates application session only at successful atomic redemption. LINK rechecks referenced CONNECT_GOOGLE proof freshness/ownership/original session and consumes proof with unique association and handoff in one transaction; no replacement session. REAUTH issues a purpose-bound proof for already linked identity. Never store raw handoff code or Google tokens.

## oauth_browser_slots

id UUID PK; slot_secret_hash BYTEA UNIQUE; generation INTEGER >=1; current_attempt_id nullable UUID FK; expires_at. Opaque cookie is slot reference plus fresh secret, not application authentication. Existing valid slot is locked when creating a new attempt; increment generation, rotate secret, supersede prior attempt and its unused handoff. For initiation only, a previous cookie secret proven by an unexpired attempt binding in the same slot is recognized as belonging to that slot; this lets overlapping requests supersede one another rather than creating separate active slots. Index (browser_slot_id,browser_binding_hash,expires_at). Callback correlation still requires the current secret and generation; a previous secret cannot complete its superseded attempt. Callbacks never set, replace, refresh or delete this cookie, on success or failure. Consume/invalidate only the correlated server-side attempt; a stale or uncorrelated failure mutates no newer state. Expire cookie Max-Age=300, Secure/HttpOnly/SameSite=Lax, Path=/; no authentication outside handshake handlers. Frontend serializes every Google initiation request, not just the first: await the complete response (including browser cookie processing) before issuing another initiation, across LOGIN/LINK/REAUTH and coordinated tabs. Do not issue a replacement while an earlier request is still in flight, even after UI cancellation. Server generation checks reject stale attempts but cannot control Set-Cookie response ordering. If clients violate serialization and initiation responses arrive out of order, mismatched cookie/generation fails safely: wait for all pending initiations to settle, discard stale start URLs/handoffs and restart a serialized flow. Missing/expired cookie requires the same restart; callbacks never repair it with Set-Cookie. Retained cookie expires five minutes after its last initiation; replay remains invalid because server attempt consumption is authoritative.

## Request admission

No rate-limit persistence or admission/finalization transactions exist. V14 removes the historical V13 accounting tables and reference columns without changing accepted business state; applied V13 remains immutable.

## verification_mail_outbox

id BIGINT PK; challenge_id UUID FK; encrypted_payload BYTEA nullable after terminal deletion; nonce/key_id; state PENDING/LEASED/SENT/FAILED/EXPIRED; attempt_count; next_attempt_at/lease_until/expires_at. Index state/next_attempt_at. AES-GCM payload has recipient/code/challenge/template only. Short SKIP LOCKED lease transactions; SMTP outside locks; retries after 5s/30s/120s, at most four sends total and never beyond challenge expiry. Delivery is at-least-once; duplicate same-code email is possible. Superseded messages skip dispatch where possible; in-flight old code remains invalid. Delete ciphertext at delivery/terminal completion, within 15 minutes after expiry if interrupted while running, or before dispatch on recovery after downtime.

## Transaction and lock ordering

Business transactions retain atomic domain mutations and outbox writes. Never hold DB locks across Google/SMTP calls.

Pending operations: pending row → its current challenge → related outbox rows sorted ID. Confirmation then performs user uniqueness insertion through UserService, assigns role and creates new session/refresh in the same transaction; no existing user is authenticated/updated. Conflicting pending/Google creation relies on users email unique constraint; rollback entire losing creation and handle outcome through a fresh boundary. No catch-and-continue in rollback-only JPA transaction.

Existing-user operations: user owner row → owner-bound proofs sorted UUID → attempt/handoff/challenge rows sorted table/name+UUID → application sessions sorted UUID → refresh rows sorted ID → related outbox rows. Recheck owner/eligibility/purpose/freshness/current session after waiting. LINK consumes referenced proof, handoff and association together; failures rollback association and successful-consumption changes. Invalid OTP checks leave business state unchanged.

Browser slot updates use a separate short transaction; authorization-state mutation and callback completion lock browser slot → attempt, matching initiation and avoiding an attempt/slot FK deadlock. Never wait on user/proof locks while holding the slot lock. Handoff redemption acquires the slot for its final generation check after all owner/proof/handoff/session work and retains it through commit; stale generations roll back all domain changes. Business completion requires matching active slot generation. Callback responses emit no Set-Cookie for correlation, so delayed callback responses cannot erase newer browser state. Cleanup uses the same owner-specific order or isolated leaf-only deletion where no owner mutation occurs; delete dependent rows before FK parents. Proof/session cleanup must remain compatible with existing auth session cleanup.

## Cleanup and validation obligations

Expired state is rejected by request checks immediately. Delete handshake/handoff/proof/pending secrets within 24 hours of expiry; remove challenges after expiry plus 24 hours. Outbox payload deadline is stricter as above. Scheduler runs at least every minute with bounded batches; startup purge of overdue payloads precedes worker dispatch; backlog metrics identify deadline risk, not claim an unbounded backlog meets deadlines. Tests cover exact bounds with controlled clocks/DB time abstraction, populated legacy upgrade, both provider constraints, exclusive challenge ownership, pending credential rotation, proof consumption/races, unrestricted repeated requests.
