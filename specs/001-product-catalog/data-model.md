# Data Model: Backend Product Catalog

This is a proposed Flyway/JPA design for [spec.md](spec.md), not an applied database schema. All IDs in these five tables are UUID. JPA associations default to LAZY, enums map as strings, timestamps use Java `Instant`/PostgreSQL `TIMESTAMPTZ`. No Inventory table or product-level price is part of this feature.

## Relationships

```text
categories (optional parent) 1 ── * categories
categories 1 ── * products
products 1 ── 1..* product_variants
products 1 ── 0..10 product_images
products 1 ── * product_image_uploads
product_image_uploads 0..1 ── 1 product_images (when PUBLISHED)
```

The child minimums and gallery maximum are business invariants checked by trusted catalog data validation and image completion transactions, with deferred database constraint triggers as a final guard at commit. Conventional FKs alone do not express them.

## Tables and fields

| Table | Columns (proposed PostgreSQL types) | Relationships and integrity |
|---|---|---|

| `products` | `id UUID PK`, `category_id UUID NOT NULL`, `name TEXT NOT NULL`, `description TEXT NULL`, `status VARCHAR NOT NULL` | FK category; nonblank name; status CHECK in DRAFT/PUBLISHED/ARCHIVED, with no implicit PUBLISHED default; product must have ≥1 variant before public use |
| `product_variants` | `id UUID PK`, `product_id UUID NOT NULL`, `sku TEXT NOT NULL`, `option_combination JSONB NOT NULL`, `selling_price NUMERIC NOT NULL` | FK product; nonblank SKU; case-insensitive catalog-wide SKU unique index; JSON object CHECK; per-product unique option map; whole-value selling price CHECK. No unapproved positivity, price cap, weight unit, or per-variant currency |
| `product_images` | `id UUID PK`, `product_id UUID NOT NULL`, `object_key TEXT NOT NULL`, `alt_text TEXT NOT NULL`, `content_type VARCHAR NOT NULL`, `byte_size BIGINT NOT NULL`, `width INTEGER NOT NULL`, `height INTEGER NOT NULL`, `display_order INTEGER NOT NULL`, `is_primary BOOLEAN NOT NULL`, `created_at TIMESTAMPTZ NOT NULL` | FK product; unique object key; unique product/order; partial unique product where primary; nonblank alt/key, format allowlist, size 1..10485760, positive dimensions, nonnegative order |
| `product_image_uploads` | `id UUID PK`, `product_id UUID NOT NULL`, `preparer_subject TEXT NOT NULL`, `staging_key TEXT NOT NULL`, `durable_key TEXT NULL`, `claim_token UUID NULL`, `claim_expires_at TIMESTAMPTZ NULL`, `proposed_content_type VARCHAR NOT NULL`, `proposed_byte_size BIGINT NOT NULL`, `alt_text TEXT NOT NULL`, `state VARCHAR NOT NULL`, `prepared_at TIMESTAMPTZ NOT NULL`, `expires_at TIMESTAMPTZ NOT NULL`, `verified_at TIMESTAMPTZ NULL`, `published_at TIMESTAMPTZ NULL`, `failed_at TIMESTAMPTZ NULL`, `product_image_id UUID NULL` | FK product/image; unique staging key, unique nonnull current durable key, unique nonnull product_image_id; state CHECK; paired nullable claim fields; nonblank preparer and metadata; bounded proposed size and type; expiry later than preparation; PUBLISHED requires `published_at < expires_at`, where `published_at` is the final server-side eligibility-check time, not physical commit time |

`preparer_subject` is an opaque stable ID from the verified authentication principal. There is no auth/User table in this checkout, so no invented cross-domain FK. The final integration must guarantee that the subject cannot be caller supplied and remains stable across token renewals. Do not log raw tokens.

## Indexes and constraints

- `idx_products_status_id ON products(status,id)` supports PUBLISHED ID pagination; `idx_products_category_id` supports category ownership.
- `idx_product_variants_product_id`, `idx_product_images_product_id`, and `idx_product_image_uploads_product_id` support batched reads and ownership checks. Add cleanup indexes on `product_image_uploads(state,expires_at)` and `product_image_uploads(state,claim_expires_at)`.
- `uk_product_variants_sku_ci ON product_variants(lower(sku))` is a unique expression index. Trim/blank validation rejects whitespace-only SKU; do not silently rewrite approved SKU values unless a later contract defines normalization.
- `uk_product_variants_product_id_option_combination` covers the JSONB map, so key order does not permit duplicates. A JSON structure CHECK guards object shape; deferred validation guards flat string values and nonblank keys/values. The price CHECK requires a finite whole number (for example, reject PostgreSQL nonfinite NUMERIC values and require `selling_price = TRUNC(selling_price)`).
- `uk_product_images_object_key`, `uk_product_images_product_id_display_order`, and partial `uk_product_images_product_id_primary WHERE is_primary` protect key, order and at-most-one-primary races.
- `uk_product_image_uploads_staging_key`, `uk_product_image_uploads_durable_key`, and `uk_product_image_uploads_product_image_id` protect upload identity/finalization.
- Deferred constraint triggers on product/variant changes reject a committed product with zero variants, nested/nonstring or blank option keys/values, and an empty map when the final variant count exceeds one. Deferred triggers on image insert/update/delete reject a committed nonempty gallery with zero primary or over ten images. The upload deadline is enforced by the final conditional publication update, not by a deferred deadline trigger: under Product then upload row locks, sample PostgreSQL `clock_timestamp()` once, require it to be strictly before `expires_at` and `claim_expires_at`, require the current VERIFIED state and fencing token, and record that sample as `published_at`. A CHECK guards `published_at < expires_at` for PUBLISHED rows, but does not claim to check physical commit time. Before count checks, triggers acquire each affected Product parent row `FOR NO KEY UPDATE`, then run a fresh count query after the lock is acquired; writers lock affected Product rows by ascending UUID before child mutations and lock an upload row after Product when both are needed. At READ COMMITTED, the parent lock serializes final checks against concurrent child changes. A deadlock aborts a transaction rather than permitting invalid data; tests must exercise concurrent deletions/insertions. Deferred checks allow inserting a Product then its first variant, or switching a primary image, within one transaction.
- Name all FKs/CHECKs according to the constitution's convention. Use a new `V...__...sql` Flyway migration under `demo/src/main/resources/db/migration`; do not edit an already applied migration. JPA schema validation should check mappings against Flyway, never `ddl-auto=create/update`.

An image's `content_type` is the verified actual type, not a client claim. The object key is a private storage address, not a URL. `ProductImageUpload.durable_key`, `claim_token`, and `claim_expires_at` are committed together before copy. Each attempt gets a distinct key under an upload-ID-scoped private prefix; an earlier attempt's key may cease to be the current DB key but remains discoverable by a scoped S3 listing. No durable key becomes a public gallery image until the image row and PUBLISHED state commit together.

## Validation and transaction rules

1. A trusted initial-data or future ADMIN product writer explicitly sets status and creates at least one variant in the same transaction. Multiple variants each require a nonempty flat map with nonblank string keys/values. A one-variant product may use `{}`. Reject fractional selling price; do not round. Deferred constraints reject invalid committed data even if a writer bypasses service validation.
2. Public reads reject invalid catalog data rather than present a variantless product as valid. They filter status PUBLISHED in SQL, recheck all candidate statuses before DTO projection, and do not reveal DRAFT/ARCHIVED information. For image-bearing results the service obtains `FOR SHARE` on Product rows in ascending UUID order, rechecks status under lock, and signs URLs locally before releasing locks. A Product status update on the same row cannot commit between that check and signing. The converter only maps the service-approved URL; the signing transaction is write-capable because it takes a row lock.
3. Prepare checks product existence and declared type/size/alt text. It records `prepared_at` using one PostgreSQL `clock_timestamp()` sample and `expires_at = prepared_at + 15 minutes`, so the session and final eligibility check share the database clock; the presigned PUT URL expires no later than that session. Count is rechecked on completion because another upload may complete meanwhile.
4. A short publication transaction locks the owning Product row, then reads gallery state and reserves an available order. First image must be primary; later image defaults to the next free append position. Explicit occupied order → 409, no reordering. Selecting a new primary updates the old primary to false and inserts the new true primary in the same transaction. The unique partial index guards concurrent mistakes. Product lock is the common serialization point for all gallery writers.
5. `PREPARED → VERIFIED → PUBLISHED` is the successful state path. First completion after `expires_at` fails, and EXPIRED is recorded once no live claim remains; invalid content marks FAILED. The service validates staged bytes before claiming; a conditional DB update commits VERIFIED, a fencing UUID, a finite claim lease (proposed two-minute configurable default) and an attempt-specific durable key before S3 copy. A claim can be renewed only by its token, but does not extend the final eligibility deadline. Another same-preparer request can reclaim an expired lease with a new token/key only before session expiry. Starting completion before expiry never substitutes for the final database-side eligibility check. PUBLISHED replay returns the existing image even after expiry. A stale token cannot publish, and its distinct private key is later cleaned. Completion verifies product ID and preparer before any object work.
6. No transaction remains open for S3 HEAD/GET/COPY/DELETE. After a committed claim, copy the validated source conditionally and verify final bytes/digest. In a separate service transaction lock Product then upload, check current token/lease and gallery state, flush image/gallery changes, then make the final business write a conditional PUBLISHED update sampling PostgreSQL `clock_timestamp()` once. A zero-row result aborts the entire transaction and its image insert; a successful result records `published_at` from that sample and publishes only if the transaction commits, even when physical commit follows session expiry. Repositories provide only locks, conditional updates and persistence; the service owns workflow and transactions. If copy or DB commit fails, the durable intent and upload-scoped prefix permit an authorized retry with a pre-expiry final eligibility check or cleanup. The scheduled worker locks the upload row, checks state/token/lease and expiry, then conditionally marks abandoned work EXPIRED or recorded failed work FAILED in its own short service transaction; it never acts as ADMIN, reclaims for publication, creates an image, or disturbs a live claim. Only after terminal EXPIRED/FAILED commits may it delete that upload's unreferenced private objects; for a PUBLISHED upload it may delete old unreferenced attempt keys but never its referenced image key. It performs deletion outside DB transactions after rechecking committed image references, repeats safely after crashes, and finishes within 24 hours of expiration/failure. Terminal state fences later publication of a deleted key; a crashed worker cannot leave an indefinite claim.

## API-facing projection

`ProductSummary` exposes id, name, immediate category {id,name}, and nullable primaryImageUrl. `ProductDetail` adds description, nonempty variants, and images ordered by displayOrder. Each variant exposes id/SKU/options and `sellingPrice: {amount, currency: VND}`; each image exposes id, a dynamically signed URL, alt text, dimensions, order and primary status. Status, object keys, upload sessions, preparer IDs and variant weight are never returned by public reads.
