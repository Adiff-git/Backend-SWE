# Research: Backend Product Catalog

All product rules below come from [spec.md](spec.md). This document resolves implementation choices; it does not approve new business rules or claim that the proposed dependencies are installed.

## Decisions, rationale, alternatives

### PostgreSQL model and price

- **Decision**: New versioned Flyway migrations create five plural snake_case tables with UUID PKs and named constraints. Use `VARCHAR` plus CHECK for statuses, `JSONB` for option maps, `NUMERIC` with a whole-value CHECK for selling price, and no product-level price/currency column. Java holds exact values as `BigDecimal` with a required zero scale; the API amount is a JSON integer in whole VND.
- **Rationale**: PostgreSQL JSONB compares object maps independent of key order, permitting `UNIQUE(product_id, option_combination)`. An expression unique index on `lower(sku)` enforces catalog-wide case-insensitive SKU uniqueness. `NUMERIC` avoids an unapproved price cap while rejecting fractional values through a CHECK. Do not reject zero as a business rule.
- **Alternatives considered**: Option tables add unapproved vocabulary/management; `BIGINT` silently imposes a maximum; PostgreSQL enum makes status evolution harder; application-only SKU uniqueness races under concurrency.
- **Sources**: [PostgreSQL JSON types](https://www.postgresql.org/docs/17/datatype-json.html), [expression indexes](https://www.postgresql.org/docs/17/indexes-expressional.html), [numeric types](https://www.postgresql.org/docs/17/datatype-numeric.html).

### Minimum relationships and gallery rules

- **Decision**: Required foreign keys for Product → Category and Variant/Image/Upload → Product. Category parent is optional and self-referencing. A partial unique index on `product_images(product_id) WHERE is_primary` gives at most one primary; `UNIQUE(product_id, display_order)` and unique object keys protect order/key collisions. Trusted initial-data and later write paths validate at least one variant, no empty map for multiple variants, at most ten images, and one primary when images exist. Deferred constraint triggers acquire the affected Product parent row `FOR NO KEY UPDATE` before checking final cross-row state at commit, including direct imports. Writers lock affected Product rows by ascending UUID, then upload rows when both are needed. Image completion serializes gallery changes in a short service transaction.
- **Rationale**: FKs and row unique indexes cannot enforce nonempty child collections or max count. Deferred checks allow parent/child creation in one transaction while rejecting an invalid commit; the parent lock serializes concurrent final-child and gallery checks at READ COMMITTED. Service checks give clearer errors. Trigger tests must actually commit and include concurrent writers; `@DataJpaTest` default rollback alone cannot exercise deferred checks.
- **Alternatives considered**: Application-only checks would not protect trusted direct SQL imports; immediate triggers would reject valid parent-then-child inserts; two collection fetch joins can multiply rows.
- **Sources**: [PostgreSQL partial indexes](https://www.postgresql.org/docs/17/indexes-partial.html), [constraints](https://www.postgresql.org/docs/17/ddl-constraints.html), [locking](https://www.postgresql.org/docs/17/explicit-locking.html), [application-level consistency](https://www.postgresql.org/docs/16/applevel-consistency.html), [Spring Boot JPA test rollback](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html).

### Catalog reads

- **Decision**: Page PUBLISHED Product IDs with fixed `id ASC`, then batch category/primary-image metadata for those IDs. Detail loads product/category and separately variants and ordered images. The service rechecks all candidate statuses before DTO projection. Before signing, it locks image-bearing Product rows `FOR SHARE` in UUID order, rechecks PUBLISHED under that lock, and signs locally before releasing it. A future status writer must update the same Product row transactionally, so it cannot commit an unpublish between the final check and signing. The converter only maps prepared values. Do not fetch-join collections into a pageable query.
- **Rationale**: Bounded database query count at size 100 and no duplicate/missing products from join-expanded pages. PostgreSQL READ COMMITTED permits a concurrent status change between page/count/metadata statements; spec only requires stable results over an unchanged catalog, but new signed URLs require an interlocked final eligibility check. The service transaction that acquires `FOR SHARE` must be write-capable even though the HTTP operation is read-only; pure no-image reads can remain read-only.
- **Alternatives considered**: Per-product lazy traversal causes N+1; pageable collection fetch joins can page in memory; REPEATABLE READ is unnecessary for stated semantics.
- **Sources**: [Hibernate fetch join guidance](https://docs.hibernate.org/orm/7.0/querylanguage/html_single/#_association_fetching), [PostgreSQL transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html).

### S3 upload integrity

- **Decision**: Private bucket; globally unique staging and attempt-specific durable keys. A verified ADMIN prepares a presigned PUT and durable PREPARED session whose `prepared_at` and `expires_at = prepared_at + 15 minutes` derive from one PostgreSQL `clock_timestamp()` sample; the PUT URL expires no later than the session. Completion verifies ownership, first-call expiry, staged bytes and source ETag/version/digest. A short committed service transaction conditionally records VERIFIED, a fencing claim token, bounded lease and upload-scoped attempt key *before* S3 copy. The service conditionally copies the validated source and verifies final bytes/digest outside DB locks. A second service-owned transaction locks Product then upload, checks token/lease and gallery rules, stages ProductImage, and uses a final conditional PUBLISHED update under those locks. That update samples PostgreSQL `clock_timestamp()` once, requires the sample to precede both session and claim-lease expiry, and writes it as `published_at`; zero rows means rollback, including the image insert. The transaction may physically commit after session expiry if this final check passed before expiry, but no image is published unless commit succeeds. Repositories only supply persistence, locks and conditional updates. A successfully committed publication can be replayed after expiry with the same image.
- **Rationale**: `clock_timestamp()` evaluates current PostgreSQL server time at the final locked eligibility statement rather than the transaction start. Locking and the claim-token predicate prevent concurrent cleanup or another completion from changing the outcome before commit. The exact physical commit instant is not used as the deadline and is not claimed to be enforceable by a deferred trigger. A presigned PUT URL can be reused and overwrite the same staging key until expiry; publishing it directly would let a client change public bytes after validation. The conditional copy or version selection closes the validation-to-copy race. A stale worker uses a different attempt key and cannot publish after losing its fenced claim. If backend/storage cannot prove final bytes match validation, completion fails.
- **Alternatives considered**: Direct-to-final PUT lacks a safe publication boundary; ETag alone is not assumed to be a cryptographic checksum; holding DB locks across S3 calls increases contention and still cannot create atomic S3/DB transactions.
- **Sources**: [PostgreSQL time functions](https://www.postgresql.org/docs/current/functions-datetime.html), [PostgreSQL conditional UPDATE and RETURNING](https://www.postgresql.org/docs/current/sql-update.html), [AWS presigned upload behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/PresignedUrlUploadObject.html), [AWS CopyObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html), [AWS Java 2.x presign](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/examples-s3-presign.html), [OWASP file upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

### Upload recovery and signed delivery

- **Decision**: Upload sessions persist current claim token/lease, current durable key, timestamps and final image ID. The technical claim lease has a configurable proposed two-minute default and can be renewed by its token, but never extends the 15-minute final-eligibility deadline. Only the same verified preparer may reclaim an expired claim before session expiry with a new token/key. The scheduled worker is cleanup-only: it must never impersonate ADMIN, reclaim for publication, or create a ProductImage. It locks the upload row in a short transaction, rechecks state, lease and server-side expiry, and conditionally marks abandoned work EXPIRED or recorded invalid/failed work FAILED; a live valid claim is left alone. Publication and terminal transition serialize on that row, so a pre-expiry eligible transaction can commit after expiry without cleanup deleting its key, and PUBLISHED is never reversed. Outside DB transactions, cleanup scans upload-ID-scoped private prefixes only after EXPIRED/FAILED commits, or for old attempt keys of an already PUBLISHED upload; it checks committed image references before deletion and retries after crashes or competing workers. The terminal state fences any later attempt to publish a deleted key. Reconcile expired/FAILED staging and unreferenced durable keys within 24 hours. Generate five-minute signed GET URLs only for PUBLISHED products; never persist or log them.
- **Rationale**: PostgreSQL rollback cannot undo S3 copy. Recording intent/outcome permits recovery after crash or DB failure; private unreferenced objects never become public. Previously issued signed URLs may remain usable up to the approved five minutes after unpublishing.
- **Alternatives considered**: S3 lifecycle expiration alone is too coarse for the 24-hour recovery contract; public bucket/object ACL violates private access.
- **Sources**: [AWS presigned URL limitations](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html).

### Image decoder, SDK, and local tests

- **Decision**: Propose AWS SDK for Java 2.x S3 client/presigner and a vetted WebP-capable decoder (for example TwelveMonkeys ImageIO WebP) because JDK ImageIO handles JPEG/PNG but has no standard WebP reader. Decoder output must confirm actual format and positive dimensions with bounded parsing. Configure AWS region/endpoint by environment. For LocalStack tests, enable signature validation and use a browser-reachable presigned host.
- **Rationale**: Claimed MIME/filename is not proof of image content. AWS SDK and decoder are absent from the POM and need constitution-required approval. LocalStack's default signature behavior would make expiration tests misleading.
- **Alternatives considered**: Trusting client `Content-Type`; proxying full image bytes through the backend; requiring production AWS credentials in tests.
- **Sources**: [TwelveMonkeys ImageIO](https://github.com/haraldk/TwelveMonkeys), [AWS endpoint configuration](https://docs.aws.amazon.com/sdk-for-java/latest/developer-guide/endpoint-config.html), [LocalStack S3](https://docs.localstack.cloud/aws/services/s3/).

### Authentication and test discovery

- **Decision**: Define a required integration contract: separately approved authentication verifies Bearer JWT and exposes an immutable principal ID plus trusted ADMIN/CUSTOMER authority. Upload prepare/complete require ADMIN; completion compares principal ID to the stored preparer. Until that contract exists, upload routes remain inaccessible. A Security `AuthenticationEntryPoint` handles filter-chain 401 and `AccessDeniedHandler` handles filter-chain 403 as sanitized ProblemDetail; MVC advice handles service-level 403. MockMvc security tests may be drafted with mock principals before the integration exists, while activating POST routes remains blocked. PostgreSQL commit and concurrency tests exercise Flyway constraints; mock S3 and LocalStack cover storage. Configure/verify Maven Failsafe for `*IT` before CI coverage claims.
- **Rationale**: Security starter declares a library, not working identity/authorization. Current Surefire defaults do not discover `*IT`, despite constitution naming. Proposed new dependencies/plugins require approval.
- **Alternatives considered**: Hardcoded ADMIN/test header in production; treating any authenticated user as administrator; reporting `mvn verify` as integration coverage without discovery evidence.
- **Sources**: [Spring Boot application testing](https://docs.spring.io/spring-boot/reference/testing/spring-boot-applications.html), [Maven Surefire defaults](https://maven.apache.org/surefire/maven-surefire-plugin/test-mojo), [Testcontainers LocalStack](https://java.testcontainers.org/modules/localstack/).

### Final team responsibility and evidence boundary

- **Decision**: The Product Catalog backend owner retains public listing/detail, catalog data integrity and signed public image-read verification. The Product Image Upload teammate owns pending T051–T055 and T057–T062, including upload service/lifecycle, upload security integration, recovery, LocalStack infrastructure, and T061 storage tests. Previously completed T001–T050, T056 and T064 stay completed and their code/tests remain available to both owners. The separate authentication owner supplies verified JWT/ADMIN identity; the upload teammate integrates it without creating a bypass or assuming authentication is already present.
- **Handoff inputs**: Endpoint, region, private bucket name/setup, disposable credential injection via environment or AWS SDK provider chain, browser/test-client reachable signing host, required signed headers, signature-validation setting, `staging/{uploadId}/{randomKey}` and `final/{uploadId}/{randomKey}` key conventions, private bucket/public-access and IAM or equivalent policy, reproducible test commands/reports, and documented LocalStack versus AWS S3 behavior. An anonymous unsigned object-key denial claim needs an enforcing environment; LocalStack behavior alone is insufficient if its policy enforcement is disabled. No credential values belong in the repository.
- **Shared gates**: T063's GET contract slice, T065's current public-read build/discovery evidence and T066's listing/detail, integrity, SC-004 and SC-005 records can be prepared by the public-read owner now. The upload teammate owns their POST/security contract, upload/LocalStack/CI inputs and lifecycle/recovery verification. Complete T063/T065/T066 only after both slices and full branch integration pass. This is task ownership, not a change to FR-015–FR-019 or the API; mocked adapter tests do not replace real storage evidence, and missing teammate evidence is not a reason to relax private-object requirements.

## Deferred questions that do not block this plan

The spec intentionally leaves zero-price policy, SKU character/length restrictions, variant weight unit, category navigation, and initial-data ownership open. This plan adds no corresponding restriction, field exposure, endpoint, or seed data. Trusted initial data is required to create a visible product, and its source must be agreed before operational rollout. Dependency versions, S3 bucket/endpoint values, deployment credentials, and the authentication implementation are technical integration choices/prerequisites for later authorized work.
