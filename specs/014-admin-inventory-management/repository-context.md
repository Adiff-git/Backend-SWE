## Transactions, security and design candidates

- Checkout uses READ COMMITTED, checks a successful receipt before mutable-state validation, fences by owner/key, locks customer-owned resources and Catalog Products before Variants in stable order, then locks eligible balances in original UUID order. The transaction persists order, allocations, receipt and accepted cart changes together. Catalog aggregate writes claim Product before affected Variant rows and can also take the taxonomy gate. Cancellation and completion lock the owning Order before ordered balances and then lock owned reservations. The V25 deferred validator avoids taking an Order lock after a balance lock. - Two Admin writes must use current counters, with accepted deltas accumulating. Admin versus Checkout must revalidate reservable units after acquiring mutation protection. Cancellation can make a decrease valid by releasing units. Completion changes the same physical and reserved counters, so an earlier absolute count could become stale. A Catalog transition racing a write requires serializing eligibility validation with its current state. Avoid introducing a balance-to-Catalog or balance-to-Order reverse dependency. An ambiguous retry of a delta can duplicate stock even if row locking is correct. Existing tests exercise competing Checkout, terminal actions, lock waits and rollback. Admin races need dedicated coverage in a later phase.
