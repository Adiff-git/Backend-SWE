# Voucher data model

Implemented as Flyway V26 in the working tree; execution evidence is recorded in [implementation-validation.md](implementation-validation.md). Preserve V1–V25 and existing UUID/Long contracts. All new PKs id BIGINT identity, UTC TIMESTAMPTZ/Instant, scalar or LAZY mappings, no unsafe Lombok/cascade deletion. Money NUMERIC finite nonnegative whole VND within existing supported digit bound; exact Java BigInteger. Named CHECK/UNIQUE/FK constraints required, names below must stay within PostgreSQL63-byte limit.

## Voucher-owned tables

### vouchers

id; code VARCHAR(64) normalized trimmed uppercase ASCII [A-Z0-9_-], unique uk_vouchers_code; title nonblank, description nullable; discount_type FIXED_AMOUNT/PERCENTAGE; discount_value NUMERIC positive (fixed integral, percentage<=100 and scale<=2); minimum_subtotal NUMERIC integral>=0; maximum_discount NUMERIC nullable integral>=0 (percentage only); valid_from/valid_until nullable with start<end when both; enabled BOOLEAN; global_usage_limit BIGINT nullable>0; per_customer_usage_limit BIGINT nullable>0; redeemed_count BIGINT>=0. Counts cannot exceed their nonnull limits. No administrative/public creation route or seed. Code normalization does not create a customer code-claim workflow.

Current definition edits never rewrite historical snapshots. Definition deletion RESTRICT while any ownership or historical reference exists; no ON DELETE CASCADE.

### voucher_customer_usages

id; voucher_id; customer_id; redeemed_count BIGINT>=0; unique(voucher_id,customer_id) and unique(id,voucher_id,customer_id). Restrictive FK users/vouchers; index idx_voucher_customer_usages_customer_id_voucher_id. This is the durable user–voucher ownership/usage relationship, created only by explicit administrator fixture provisioning with grants. No runtime preview upsert or missing-relation exemption. Personal redeemed_count is lifetime committed count across grants; new grants do not reset it. Null personal limit remains unlimited numerically, but available grants still required.

### voucher_entitlements

id; voucher_customer_usage_id; voucher_id; customer_id; granted_at; state AVAILABLE/CONSUMED; consumed_at nullable. Composite FK to usage identity triple; unique(id,customer_id), unique(id,voucher_id,customer_id). One row=one granted use. AVAILABLE iff consumed_at null; CONSUMED has immutable consumed_at>=granted_at and exactly one matching redemption. Identity/ownership/granted_at immutable. Consumed row immutable and retained; remove from active inventory by filtering state, never deletion. Available rows are not consumed by expiry, disable or cart invalidation. External grant administration/revocation API is not implemented; availability checks reject any unavailable grant safely.

Index idx_voucher_entitlements_customer_id_state_id. For canonical code-order pagination join only owned grants and definition; project scalars, count first and use bound long-offset native content if offset>Integer.MAX_VALUE and nonempty (as established Order paging). No invalid JPA narrowing or lazy per-grant query.

### voucher_redemptions

id; voucher_id; voucher_entitlement_id; voucher_customer_usage_id; customer_id; order_id; redeemed_at; code_snapshot/title_snapshot/type_snapshot/value_snapshot/minimum_subtotal_snapshot/maximum_discount_snapshot; calculation_base; applied_discount. Unique order_id and voucher_entitlement_id. Composite restrictive FK (order_id,customer_id)→orders; entitlement identity triple and usage triple must agree with voucher/customer. Add matching composite unique keys as needed, not independent FKs that allow foreign attribution. Snapshot money/type/value/time rules mirror valid definitions; snapshot discount is exactly floor(min(raw,optional percentage cap,B)) and payable relation. redeemed_at equals placement and consumed_at; Inventory reserved_at and receipt created_at use this same authoritative event. It is sampled only after all required Voucher locks are acquired and protected data reread; validity is evaluated then, never using a caller pre-lock timestamp. B>0; discount may be0 (percentage rounding or zero cap). A zero actual discount still consumes the explicitly selected valid entitlement once; do not invent a positive-discount eligibility rule.

History immutable and deletion restricted. No restored flag, cancellation outcome, refund/return grant or status-driven quota rule. Deferred validation requires exact owner/entitlement/order snapshot correspondence and one redemption for a consumed grant; no redemption for AVAILABLE. Counts reconcile to all committed redemptions (not filtered by current order status); this is original purchase accounting, not a decision about future cancellation policy.

## Cart-owned extension

carts.voucher_entitlement_id nullable plus voucher_selection_revision BIGINT>=0 (increment safely on explicit select/remove/automatic clear/checkout clear; overflow safe conflict). Composite ownership FK to (entitlement id,customer id) using carts.user_id, with restrictive deletion. Cart may reference a later-invalid entitlement until next successful evaluation; do not add a cross-domain trigger silently clearing it on expiry/consumption. No preview amount persisted. Missing-cart read/remove never creates it. All cleanup uses locked current cart and current revision; never act on preflight selection. Consumed cart reference must be cleared by the successful checkout transaction that consumed it; final integrity requires no retained selection pointing at its consumed grant.

## Order-owned extension

orders.voucher_discount NUMERIC NOT NULL DEFAULT0; voucher_snapshot JSONB nullable, with full immutable original public explanation (walletEntitlementId,voucherId,code,title,discountType,discountValue,minimumSubtotal,maximumDiscount,calculationBase,appliedDiscount,redeemedAt). No customer usage counters exposed. No-voucher snapshot null and discount0; voucher-bearing snapshot exactly matches immutable redemption. merchandise_total still equals sum(line_total); payable_total=merchandise_total-voucher_discount>=0. Existing item rows/units/prices/line arithmetic unchanged. Add immutable discount/snapshot guard so later status changes cannot reprice history; legacy amounts remain untouched and snapshots null. The new header arithmetic CHECK applies to managed orders and all voucher-bearing orders; retained pre-Inventory (inventory_managed=false), zero-discount/null-snapshot history keeps its previously valid payable amount rather than inventing a Voucher discount. New creation commands and version2 receipts always enforce exact arithmetic.

Prepared Order creation command carries explicit merchandiseTotal, voucherDiscount, payableTotal and nullable prepared snapshot. New SQL inserts bind them separately; old total-to-both insertion must change. Order validates sum and arithmetic/coherence without owning Voucher repositories or calculating policy. Read projections prepare new fields in the existing count/content/preview/detail paths, never per-order Voucher fetch. Historical payable sorts continue unchanged.

## Receipt version2 and final integrity

New receipts2 for all new checkouts; old1 retained. ck_checkout_receipts_version accepts1/2; body constraint dispatches to strict validators by version. Preserve existing v1 function semantics including V25 stock skip codes; new v2 exact keys include voucherDiscount/voucher with unchanged item fields and skip codes. For version2 sum lines=merchandise, merchandise-discount=payable and snapshot arithmetic/types exact. Deferred original-order comparison constructs the matching version's JSON, checks source order/owner/time/redemption snapshots and never compares replay to later current status. The existing insert-only original comparison remains insert-only; no receipt rewrite/updates. Preserve address fingerprint/key scope/status201/Location.

Named integrity groups: ck_vouchers_definition, ck_vouchers_usage; ck_voucher_usages_count; ck_voucher_entitlements_state; ct_voucher_entitlements_immutable; ct_voucher_redemptions_immutable; ct_voucher_usage_integrity; ct_orders_voucher_integrity; ck_orders_voucher_totals; existing ct_checkout_receipts_integrity version-aware. Exact error allowlist selected in implementation; no broad23514→409 or SQL-message parsing. Existing v1 receipt constraints/decoder tests remain meaningful.

Deferred purchase/usage/redemption validation reconciles global/customer counts against redemptions, verifies consumed-grant attribution and order snapshot completeness; acquire definition→usage→entitlement resources in ascending IDs, never acquire existing order/user/cart/Inventory locks afterward. Cart-only deferred checks validate retained consumed state without quota locks, avoiding grant FK key-share→definition reversal; the purchase-side final validator still locks grants before checking all retained Cart references. Checkout already holds relevant rows. Projection reads of historical order for constraint checking must not add reverse locking to Order terminal flows. Treat direct SQL inconsistencies as named rollback errors; no repair/backfill guessed from missing records. Measure repeated trigger server cost separately from client statements.
