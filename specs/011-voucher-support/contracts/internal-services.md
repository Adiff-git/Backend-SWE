# Voucher internal service contracts

Implemented contract; [API](api.md), [model](../data-model.md), [research](../research.md). All source paths under demo/src/main/java/com/example/demo. Services use constructor injection, interfaces/Impl, immutable defensive Lombok request/response DTOs and Jakarta validation for applicable structure. No converter/repository workflow orchestration.

## Ownership graph

Cart→Catalog/User/Voucher; Catalog→Inventory/Storage; Checkout→User/Address/Cart/Catalog/Order/Inventory/Voucher; Order→Catalog/Inventory; Voucher→its own repositories only. No Voucher→Cart/Order/Checkout/Catalog call or foreign repository. CartVoucherService/Impl is a cart-owned facade that orchestrates wallet list/detail applicability using prepared Cart subtotal and VoucherService; VoucherController delegates one facade method, never does subtotal orchestration. CartVoucherController delegates CartVoucherService for apply/remove with existing Cart response. Voucher DTOs belong voucher/dto; Cart selection/preview DTOs belong cart/dto. Do not introduce a global integration framework.

## VoucherService / service.impl.VoucherServiceImpl

- getWalletPage(owner,page,size,preparedSubtotal) and getWalletEntitlement(owner,id,preparedSubtotal): read-only owned scalar projections and eligibility from one injected Clock observation; page0/size20 defaults are parsed by the HTTP reader and size1..100 validated by the service. No Cart fetch or grant insertion. Return domain DTOs/page seed, converter maps only prepared values.
- getPreview(owner,entitlementId,B,event): observational read of own grant/definition/usage; VoucherValidator returns safe reason, VoucherCalculator produces exact discount only if applicable; zero is a valid calculated discount. Missing ownership is safely classified for internal caller without disclosure; external facade maps404. No mutation/reservation/automatic grant creation.
- lockCheckoutVoucher(owner,entitlementId,B): join caller write transaction, discover owning definition/usage nonauthoritatively, acquire definition then usage then entitlement locks and reread current protected data. Only after all required Voucher locks are acquired, sample the injected Clock once at microsecond UTC precision; validate all exact identities/state/limits/time against B using that event. Return immutable locked quote (identities,terms,B,discount,event). Do not accept a pre-lock timestamp from the caller. If absent selection, acquire no Voucher locks and return an explicit no-voucher quote with one sampled event and zero Voucher SQL. Reject invalidity with CheckoutVoucherNotApplicableException (409 VOUCHER_NOT_APPLICABLE plus safe reason); no cleanup.
- redeemVoucher(preparedQuote,actualOrderId): same REQUIRED transaction, validate supplied quote coherence and actual prepared IDs, conditional increment global/customer counts and consume AVAILABLE entitlement, insert immutable exact attributed redemption. Each expected mutation count1, otherwise safe rollback conflict. Database constraints cross-check order snapshots/owner/time at final commit. No independent transaction/external call or current-state Order fetch. Only trusted Checkout calls this boundary; no public endpoint.

VoucherValidator owns eligibility/definition rules and safe reason precedence. VoucherCalculator owns discount arithmetic exactly once; converts percentage value to integer hundredths without truncating invalid definitions. VoucherConverter maps prepared values, no repository calls or authoritative arithmetic. Commands validate IDs/subtotal/time/required nested values; quote cannot be reused across a different order/base/owner. Repositories provide narrow scalar/lock/conditional methods, no public generic stock/quota edit service.

## Cart integration

Keep CartServiceImpl facade image candidate/preparation outside authoritative transaction. Add methods for wallet/apply/remove through CartVoucherService and proxied CartVoucherTransactionService/Impl where necessary; do not self-invoke to activate @Transactional. CartTransactionService's final response preparation owns subtotal plus VoucherService preview call, automatic cleanup and CartConverter mapping. Shared cart-owned preview helper may remove real duplication; no second subtotal engine.

GET existing cart: set existing cart timeout, lock owned parent before reading rows/selection/revision, prepare current Catalog/Inventory publication-safe state and exact subtotal, sample one microsecond Clock event and evaluate voucher. If invalid, clear only locked current selection/increment revision, return null voucher/zero discount/undiscounted total plus safe reason. Missing cart returns empty without insertion. Successful add/quantity/variant/individual/bulk mutations use the same final preparation. Preserve all original stock409 exceptions and eligibility precedence; a rejected mutation rolls cleanup back.

removeItem currently returns void: after deletion/flush explicitly recompute remaining eligible rows through no-image Catalog variant read, evaluate/clear selected voucher and flush before successful204. Do not introduce unnecessary S3 signing for deletion. removeVoucher locks existing cart, clears only selection and returns204; no absent-cart creation. Apply/reapply validates owned entitlement under current cart state before setting it; return full response with final eligibility observation. If it becomes invalid before final response, reject/rollback replacement rather than commit a misleading successful apply. No other cart field changes; repeated same selection stays one, cleanup revisions advance safely.

Wallet facade prepares no-image eligible subtotal observationally through cart-owned read service and calls VoucherService; no mutation/cleanup, image calls or reverse dependency. Page/detail is an observation. All GET Cart cleanup is voucher-selection-only and explicitly write-capable; do not set readOnly=true there. Catalog lock graph precedes Voucher observations; no network preparation under new locks.

CheckoutCartSeed adds selectedEntitlementId and selectionRevision, captured only under existing cart parent lock. CartCheckoutService.consumeCheckoutItems retains exact included row predicates. Add clearCheckoutVoucher(owner,seed) conditional on current cart/selection/revision; called only on new successful voucher-bearing execution. Current cart lock already serializes it, but affected-count check protects stale/prepared commands. Never clear a new selection on replay. Empty/nonvoucher checkout creates no redemption; original no-voucher cart behavior remains.

## Checkout sequence and locks

Existing strict input/auth → public CheckoutService REQUIRED/READ_COMMITTED → scoped receipt-first lookup → on miss try fence and fresh acquired/busy lookup. Any receipt hit compares stored address fingerprint, version-aware decodes and returns original with zero mutable-domain work. Unsupported/corrupt version safe500, never re-execute.

New execution: user serialization; restore checkout timeout after UserService sets its own; owned address; cart lock/seed; ordered catalog product+variant locks; final existing classifier; Inventory lockAvailability on all stock candidates in sorted batches100; full-row included calculation. No included rows422. Call Voucher lockCheckoutVoucher without a caller timestamp. It acquires every required definition→usage→entitlement lock first, then samples the authoritative microsecond Clock event and validates current eligibility. Checkout uses the returned event unchanged for order placement, Inventory reservation, grant consumption, redemption and receipt creation; no earlier checkout sample or second downstream sample. Any invalid selected grant409 rolls back, never invoke Cart preview auto-clear. CreateOrderCommand carries exact merchandise/discount/payable/full immutable snapshot; created item prices unchanged. Create actual order/items, reserve those exact items using already-held balances, redeem selected grant, consume represented rows, clear captured selection, encode/decode version2 and persist immutable successful receipt before proxy commit.

Full graph: fence→user→cart→products sorted UUID→variants sorted UUID→balances sorted UUID→voucher definition→usage→entitlement→new aggregate/redemption/receipt. Re-lock Inventory only already-held balances after Voucher locks; no new stock resource may be discovered late. Existing order terminal graph order→Inventory stays untouched and makes no Voucher call. V3 deferred catalog/V23 parent locks and V25 reconciliation remain; new Voucher deferred triggers must not reverse into existing order/cart/user/balance locks. Future admin operations must use same definition-first graph; no present admin runtime path.

Preview reads are observations under READ_COMMITTED, not a guaranteed allocation; checkout locks and conditional writes provide authoritative limit safety. Post-preview concurrent invalidation is caught by independent checkout. No stronger isolation, REQUIRES_NEW, memory lock, auto retry or global pool change.

## Receipt/order evolution

CheckoutReceiptRepository insert accepts explicit new version2, not hardcoded1. CheckoutValidator accepts supported1/2 while preserving fingerprint string/namespace. CheckoutConverter delegates explicit v1/v2 codecs and response models (or equivalent version-preserving serializer) so v1 excludes new fields and v2 retains them, including no-voucher0/null. Keep max numeric digit constraint scoped to receipt mapper. No expiring image or current catalog/Voucher fetch in receipt conversion.

OrderCreationRepository binds merchandise/discount/payable separately; validator checks prepared item sum and coherence. New Order snapshot projections/pure converter supply history without Voucher service reads. Additive migration/version-aware database checks are required alongside Java codecs; don't loosen exact keys or old comparison to make tests pass. Later status changes don't rewrite snapshots. No cancellation hook, quota restoration/retention decision or consumed grant reissue is part of this feature.

## Verification/query boundaries

Use fixed number Voucher queries per preview observation or wallet page, no per-cart-item/order-item voucher fetch. Wallet list count-first plus one page projection (and bounded cart-context preparation); no entity lazy loads. Existing Cart/Catalog/Order query ceilings remain unless a measured fixed Voucher addition is documented explicitly. Measure all JDBC/native work,100/101/205 cart rows and wallet entries; report deferred function cost separately. Replay has one scoped receipt lookup, zero Voucher SQL, detached codecs0 SQL. Complete actual commit tests for missing/wrong-attribution/foreign grant, counter mismatch, later receipt failure, and multi-variant rollback. Normally discovered concurrency proves different-customer last global use, multiple-grant same-customer limit, same entitlement twice, GET cleanup versus replace/checkout and busy/acquired completed-replay freshness. Add a synchronized expiry-during-lock-wait regression: hold a required Voucher row lock in a separate transaction, observe checkout actually blocked, advance a controllable Clock from before validUntil to exactly validUntil or later, then release the lock. Checkout must sample after acquisition, reject409 with VOUCHER_EXPIRED and commit no order/receipt/redemption/usage/reservation/cart/grant change. Include a before-end success control proving all persisted purchase timestamps equal the single post-lock event. Use barriers and observed database waits, never timing sleeps as proof. Preserve old Inventory/Cart/Address and all security assertions; no weakened/duplicate suites.

Implementation notes: CartPreviewService and CartWalletReadService provide the Cart-owned preparation boundary; VoucherCacheFilter covers personalized success/filter errors. Stored Order JSON is materialized by the Order read service before conversion. Legacy nonmanaged zero/null history retains its prior payable amount; new managed/voucher-bearing purchases and version2 receipts enforce exact discounted arithmetic. Voucher aggregate validation does not run for Order status-only updates. No cancellation/confirmation/payment policy was added.

Cart-only deferred validation never takes definition/customer-usage locks after its grant FK key-share lock. It checks retained consumed state locally; purchase/redemption reconciliation retains ordered quota/usage/grant locks and verifies every consumed-grant Cart reference. This preserves final integrity and avoids the demonstrated cross-customer selection-versus-purchase deadlock. Compatible JSON body handling relies on the existing strict reader/body advice and normal message converters; missing required body400 and unsupported nonempty media415 stay distinct.
