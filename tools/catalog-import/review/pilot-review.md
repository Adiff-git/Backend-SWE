# Product Catalog pilot: human approval review

This report reviews the 50 rows in [demo-products-approval.csv](demo-products-approval.csv). It records crawled facts and questions for reviewers; it does not grant any approval. Source links are the URLs recorded by the normalizer, not newly checked live product pages. Prices are exact source `Offer.price` observations in VND, not approved selling prices.

All 50 rows remain `NOT APPROVED` for import, SKU, selling price, category, variant mapping, and publication. Approved selling-price cells are blank. The normalized candidates are structural candidates; each carries `SELLING_PRICE_UNAPPROVED`, `SKU_APPROVAL_REQUIRED`, and `VARIANT_APPROVAL_REQUIRED`. No selected row carries a structural rejection reason.

## Findings requiring review

- No exact duplicate product name or proposed catalog SKU appears among these 50 rows. Similar Meizu and Teclast names differ by RAM/storage; decide whether they should be separate products or variants before import. The importer supports one variant per approved source product.
- Product names and descriptions disagree for rows 3, 12, and 13. Row 28 has a description typo. Row 39 has a short description; many other descriptions are mostly promotional text rather than technical specifications.
- CellphoneS proposals often use URL-like SKU slugs; rows 27 and 29 use `DRS.TG.*` codes. TGDD proposals use numeric retailer IDs. None is automatically an approved catalog SKU.
- TGDD laptop prices in rows 32, 33, and 35 are non-rounded. These are still exact crawled values; their currency, present relevance, and any demo selling price require explicit review. The other prices also require approval.
- CellphoneS proposes deeper category paths; TGDD laptop and case paths are flat. Row 30 has a broad kitchen-appliance category, and TGDD case labels abbreviate "đ.thoại". Review whether categories should map to shared existing IDs before approving 39 proposed category nodes.
- All 50 propose one variant with `{}` options. Confirm that interpretation for each product, especially configuration families and phone cases with compatibility or color choices. No image is proposed for import.

## Reading the rows

The **source SKU → proposed catalog SKU** column shows the same text twice because the CSV copies the source SKU as an unapproved proposal. **Variant** is `1 × {}` for every row: one proposed variant with an empty option map, pending human confirmation. **Decisions** `I/S/P/C/V; Pub` means import, SKU, selling price, category, and variant approvals are required; publication is a separate optional approval. With publication unapproved, a later approved import would be DRAFT.

## Proposed local-development approval policy

1. **Source facts:** retain retailer, source ID, URL, name, description, source SKU, exact `Offer.price`, currency, and proposed category path as evidence. Recheck any stale or contradictory page before relying on it. Do not treat `AggregateOffer` ranges as prices.
2. **Technical validation:** require the importer dry run and read-only database preview to pass, an unambiguous category mapping, case-insensitive SKU uniqueness, a positive whole-VND approved price, a flat valid option map, and a compatible Flyway V1–V9 target. These checks establish data shape, not business permission.
3. **Business approval:** a reviewer may explicitly designate a verified source price as a *demo* selling price, or choose another price; enter that value in `approved_selling_price_vnd` and approve it separately. Review the proposed SKU, category, and single-variant boundary. Only then set `sku_approval`, `selling_price_approval`, `category_approval`, `variant_mapping_approval`, and `import_approval` to `APPROVED`. Leave uncertain rows pending.
4. **Publication:** leave `publication_approval=NOT APPROVED` for a local DRAFT import. If a demonstration needs public GET visibility, approve a small named subset separately after checking descriptions, prices, and product boundaries. Never infer publication from import approval.

Before any PostgreSQL import, resolve the flagged rows, complete the CSV approval fields, rerun `--dry-run`, inspect a `--check-db` preview against a positively identified **local-development** database, and review its current history and backup. This report and the CSV do not authorize an import.
