# Customer behavior tracking

Backend implementation for authenticated Customers only. Customer means the existing `ROLE_USER`, excluding `ROLE_ADMIN` even if both roles are assigned. No Guest/session/fingerprint tracking. No cart, order, scroll, dwell-time or recommendation algorithm. Frontend instrumentation and AI consumption are separate work; Backend alone does not establish browser-to-database tracking.

## Events and storage

V20 creates `user_behavior_events`. UUID event IDs are generated by Backend; `customer_id` references existing `users.id` (BIGINT); `product_id` references existing UUID products. Types and field combinations are CHECK constrained. `occurred_at` is server Clock time stored as TIMESTAMPTZ and returned as UTC. There is no client timestamp/identity input.

| Type | Trigger | Fields |
| --- | --- | --- |
| PRODUCT_VIEW | Frontend submits after intentional detail viewing | productId required |
| SEARCH | Frontend submits intentional search action | searchQuery required; product/source absent |
| PRODUCT_CLICK | Frontend reports selection from a list | productId required; optional sourceContext |
| WISHLIST_ADD | Backend actually creates membership | productId; no clientEventId |
| WISHLIST_REMOVE | Backend actually deletes membership | productId; no clientEventId |

Client events require UUID `clientEventId`. Only PRODUCT_CLICK allows `sourceContext`: SEARCH_RESULTS, CATEGORY_LIST, PRODUCT_LIST, OTHER; omission means unspecified. All product events submitted by clients require a currently PUBLISHED product (404 for absent/hidden). An identical retry of an already accepted event remains valid after unpublishing. GET listing/detail requests do not record anything or issue tracking queries.

SEARCH stores the submitted query verbatim for owner history and exact retry comparison, plus its normalized representation for aggregation. Existing ProductSearchNormalizer enforces 256 Unicode code points, at most 16 tokens, rejects invalid controls and non-searchable/blank text, and retains Vietnamese search normalization semantics. No arbitrary metadata, identity, timestamp, headers, IP, user-agent, payment data or tokens are stored. Unknown JSON fields and unknown/duplicate query parameters are rejected. Search text can still contain personal information; frontend should discourage submitting it and deployment must avoid request-body/SQL-parameter logging.

User deletion cascades behavior events. Product deletion also cascades its events, so historical aggregate counts can decrease. This avoids blocking catalog deletion or retaining dangling product identities. Existing application has no account-deletion endpoint or consent/opt-out subsystem; this feature adds neither. Any future account-deletion workflow must handle existing unrelated user foreign keys; behavior imposes no additional blocker. Deployment/frontend own any applicable notice/consent requirements. These controls are not a legal-compliance claim.

Indexes: unique `(customer_id,client_event_id)` (NULL allowed only for Backend Wishlist events), `(customer_id,occurred_at DESC,id DESC)` for history, and `occurred_at` for retention/analytics windows. Small bounded SQL aggregations suffice at this project's scale; no broker/cache infrastructure is added.

## APIs and security

All APIs use the existing Bearer JWT validation, live account/session state and database authorities. Missing/invalid authentication returns 401; wrong role 403. No body or query parameter can select a different history owner. All successful responses use `Cache-Control: no-store`; validation/business failures use existing ProblemDetail conventions with safe descriptions.

| Method/path | Authorization | Result |
| --- | --- | --- |
| POST /api/me/behavior/events | Customer | 201 `{ "created": true }`; identical retry 200 `{ "created": false }` |
| GET /api/me/behavior | Customer | BehaviorPage with items, page, size, totalItems, totalPages |
| GET /api/admin/behavior/overview | ROLE_ADMIN | Aggregate BehaviorOverview |

POST accepts exactly eventType, productId, searchQuery, clientEventId, sourceContext; fields must match the event type. 400 means malformed/invalid input; 404 unavailable product; 409 conflicting reuse of clientEventId. Clients cannot submit Wishlist types. No unbounded or batch ingestion endpoint exists.

History parameters: page (default 0, 0..100000), size (default 20, 1..100), eventType (optional, any of five types), from/to (optional ISO-8601 UTC instants). Defaults: now minus 90 days / now. Date interval is inclusive, ordered, at most 90 days, to cannot be future. Older requested start is clipped to retention cutoff. Expired events are always excluded, even before deletion. Sort: occurredAt DESC then id DESC; DTO includes id, eventType, productId, searchQuery, clientEventId, sourceContext, occurredAt, never customer identity. SQL uses bounded LIMIT/OFFSET plus count, with no entity hydration or N+1. Separate page requests are live snapshots; concurrent insert/delete can shift offset pagination.

Analytics parameter days is exactly 7 (default), 30 or 90. From is server-now minus days; to is server-now, inclusive. Counts include all recorded event types; mostViewedProducts/mostClickedProducts rank up to ten product UUID/count pairs by count descending then product ID. popularSearchTerms ranks up to ten normalized query/count pairs and suppresses terms from fewer than three distinct Customers. Tie-break is query ascending. All aggregation is in PostgreSQL; no raw histories are returned to administrators. Threshold suppression reduces accidental disclosure but is not anonymization. A view/click means a recorded report, not a unique human or proof of a physical browser action. No rate limiter is added (the existing project removed its request-rate limiting in V14); authenticated clients can submit fabricated interactions. Use deployment traffic controls if required.

Runtime OpenAPI is generated from the behavior controller/DTO annotations alongside existing application APIs. `docs/user-behavior-openapi.yaml` supplies the precise event unions, response schemas and retry/status contract for integration.

## Transactions and retries

Unique customer/clientEventId is enforced in PostgreSQL. INSERT ON CONFLICT DO NOTHING safely serializes concurrent retries; a subsequent READ COMMITTED read compares type, product, exact submitted query and source. Same payload returns 200; different payload returns 409. Different Customers can use the same key. Never regenerate a key for a retry; a genuinely new action gets a new UUID. No time-window deduplication suppresses legitimate actions. Idempotency records expire with raw events at 90 days (or earlier on account/product deletion), so a key reused after deletion represents a new event. No payload/key tombstones are retained past retention.

Wishlist hooks run at the service state-transition point in the same existing transaction, with MANDATORY propagation. Duplicate adds and no-op removes produce no event. A failed membership/signing operation or outer rollback rolls back events too. Tracking persistence failure rolls back the membership operation; callers receive the existing safe failure response and may retry. This deliberate coupling gives atomic correctness without asynchronous delivery or circular dependencies. A SQL role check limits all persisted events, including Wishlist hooks, to Customer accounts.

## Retention and operation

90 days means Duration.ofDays(90), independent of daylight saving. Events with occurred_at < now minus 90 days are expired; exactly at cutoff remains until time advances. History and analytics enforce this immediately. Cleanup uses the existing Spring scheduling mechanism, runs every 60 seconds after initial 60-second delay, and deletes only behavior rows in batches of 1000 using FOR UPDATE SKIP LOCKED. Each statement commits independently; at most 100 batches per invocation. Concurrent inserts and multiple application instances remain safe. A fixed cutoff per run makes deletion reproducible. Physical deletion can lag expiry by scheduler delay/backlog/outage; monitor deployment scheduling/database health. Raw events are never queryable beyond 90 days through these APIs. There is no permanent aggregate/tombstone copy.

Configuration: `behavior.retention.enabled` (default true), `behavior.retention.delay-ms` (default 60000). Disabled only in disposable tests. Operational code can invoke BehaviorRetention.cleanup() directly; there is no publicly exposed cleanup route. Test the fixed cutoff via an injected Clock. Do not disable cleanup in normal deployments.

## Frontend examples

Use an active Customer Bearer access token. Generate UUID once when an intentional action occurs, retain the payload/key until success, and retry the identical payload on a network failure or recoverable 5xx. Treat both 200 and 201 as success. Correct invalid 400 payloads; refresh/login on 401; stop on 403/404; 409 means a key was mistakenly reused for a different action and requires fixing client bookkeeping. Persist retry state only as appropriate for your frontend's privacy policy, and discard it on logout/account change.

```javascript
const event = {
  eventType: 'PRODUCT_VIEW',
  productId,
  clientEventId: crypto.randomUUID()
};
await fetch('/api/me/behavior/events', {
  method: 'POST',
  headers: { Authorization: `Bearer ${accessToken}`, 'Content-Type': 'application/json' },
  body: JSON.stringify(event)
});
```

Submit PRODUCT_VIEW after the detail is intentionally displayed, not on every render/prefetch. Keep the same action key across framework remounts/retries. Backend does not measure dwell time.

```json
{"eventType":"SEARCH","searchQuery":"Điện thoại Samsung","clientEventId":"d151a063-a28f-43b3-9d48-e6dfe068991f"}
```

Submit SEARCH on explicit search/committed search action; pagination, refetch, filter fetch and background refresh are not new search actions.

```json
{"eventType":"PRODUCT_CLICK","productId":"c0f9519d-c1ae-43fa-8909-43c6328dbfe0","sourceContext":"SEARCH_RESULTS","clientEventId":"7156c866-6c78-49fc-bfe0-a72bca5cc657"}
```

Submit click on intentional selection. Click and ensuing intentional detail view are distinct signals with distinct keys. Never submit WISHLIST_ADD/WISHLIST_REMOVE; use existing Wishlist endpoints.

```sh
curl -H "Authorization: Bearer $ACCESS_TOKEN" 'http://localhost:8080/api/me/behavior?eventType=SEARCH&page=0&size=20'
curl -H "Authorization: Bearer $ADMIN_TOKEN" 'http://localhost:8080/api/admin/behavior/overview?days=30'
```

## AI integration boundary

AI-SWE was inspected read-only. Its future behavior requirements align with Backend event UUID/type/time, canonical product UUID and query. No trustworthy service identity/authorization model exists in this Backend: ordinary Customer JWTs are not service credentials. No internal cross-user endpoint is enabled; existing security denies `/api/internal/behavior/users/{customerId}`.

Available now: owner-scoped GET /api/me/behavior with stable BehaviorPage/BehaviorEvent DTOs. Future proposed GET /api/internal/behavior/users/{customerId} (BIGINT) should reuse BehaviorService.history and the same bounded query/response contract, only after a separately provisioned, validated service principal with explicit behavior-read scope and audit/access policy is implemented. A service token must never be a Customer token or ad-hoc shared-secret header. AI-side consumption, service authentication, and personalized recommendation are pending integrations, not delivered capabilities.
